# 失败案例分析与问题排查报告

本报告逐条记录评测与演示中发现的问题：现象、证据（用例编号与轨迹位置）、原因、处理和效果。轨迹都在 `results/<运行>/traces.jsonl`，每行是一个变体在一条用例上的完整对话，可以用用例编号检索。

## 1 方法

1. 每个未达成的评分目标先由 `evals/failure_report.py` 按失败模式自动归类：服务端错误、未闭环、拆解错误、上一轮出错、检索没命中、检索命中但判断错、分类错。归类只看轨迹里的客观字段（停止原因、计划长度、检索结果里有没有标准答案），不看模型的回答内容。
2. 对每一类挑代表性用例回放完整轨迹，确认原因。
3. 能低成本验证的修改，在出问题的那批用例上做定向实验，用同样的打分规则比较修改前后。

|---|---|---|---|---|---|---|---|---|

## 3 逐条排查

### 3.1 一条 issue 报告被拆成「排查、复现、给出修复」多个子任务

- 现象：GLM-4.7-FlashX 在 10 条单轮重复 issue 用例里，有 8 条被 planner 拆成 2 到 4 个子任务，例如「调查内存泄漏的原因」「判断泄漏来自装饰器还是模型」「给出修复或绕过办法」；这 10 条一条都没有给出正确的原 issue。Gemini 3.5 Flash-Lite 在全部 30 条单轮用例里都只拆出 1 个子任务。
- 证据：`results/20261124T184625Z/traces.jsonl` 中 `glm-4.7-flashx+rag` 的 `dup-8239`、`dup-9348` 等用例，第一轮的 `plan` 字段。
- 原因：planner 的提示只说「只有明确包含几件事时才拆分」，FlashX 把一份 bug 报告理解成了一项排查工作，按排查步骤拆分；拆分之后每个子任务都在找原因、给建议，没有一个子任务负责查重。
- 处理：planner 提示 v2 加了一条规则：一份 issue 报告就是一个子任务，即分诊它，不拆成调查、复现、修复（`src/triage_agent/graph.py` 的 `PLANNER_PROMPT_V2`）。
- 效果：在同样 10 条用例上定向复测（`results/20261124T201038Z_planner-v2/`）：

  | 指标 | planner v1 | planner v2 |
  |---|---|---|
  | 只拆出 1 个子任务的用例 | 2 / 10 | 9 / 10 |
  | 找对原 issue 的用例 | 0 / 10 | 2 / 10 |
  | 每条用例工具调用次数 | 14.3 | 7.4 |
  | 每条用例耗时 | 119.6 秒 | 95.4 秒 |
  | 10 条合计花费 | 0.064 美元 | 0.021 美元 |

  拆分问题基本消失，调用次数降到约一半，花费降到约 1/3；但 8 条仍然找不到原 issue，而这 8 条的原 issue 都已经出现在检索结果里，剩下的瓶颈是 3.3 节的判重。

### 3.2 结论写进了回答，没写进结构化字段

- 现象：回答正文写着「This is a duplicate of #7687」，`duplicate_of` 字段却是空的，结构化结果因此判错。
- 证据：`glm-4.7-flashx+rag` 的 `dup-8239`、`dup-7747`（主评测）。
- 原因：模型把判断写进了自由文本，没有同步到字段；下游系统只读字段。
- 改进方向：在 `submit_triage` 的参数模型上加一条一致性校验：回答里出现「duplicate of #N」而 `duplicate_of` 为空时拒绝提交，把错误回传给模型，让它自己补上。这和现有的参数校验走同一条路径（ToolNode 把校验错误作为工具结果返回）。

### 3.3 原 issue 检索到了，判断却错了

- 现象：重复 issue 目标的检索命中率很高，正确率却低得多：GLM-4.7-FlashX 检索命中 93.3%、正确 0%；Gemini 有文档检索时命中 86.7%、正确 33.3%，没有文档检索时命中 93.3%、正确 20.0%。
- 证据：例如 `dup-8581`（原 issue #7686）、`dup-1388` 与 `dup-1151`（原 issue #655）。这几条的原 issue 和新报告描述的症状不同，维护者是按「根因相同」判的重复，例如「允许以下划线开头的字段」和「给模型加私有属性」。
- 原因：模型只看到 issue 标题和正文前 1500 字符，看不到维护者的讨论、关联的修复 PR 和测试，判断「是不是同一个根因」缺少依据。
- 改进方向：给 MCP server 加两个工具：读取 issue 的评论和关联 PR；再加一个专门的候选比对步骤，让模型对检索到的前几个候选逐一回答「修好那条能不能同时解决这条」。

### 3.4 追问时把上一轮的结论又提交了一遍

- 现象：第二轮追问时，GLM-4.7-FlashX 在 6 条多轮用例里有 5 条把第一轮的结论重新提交了一次，新问题的结论用了第 3 号子任务。Gemini 6 条里 0 条出现。
- 证据：`follow-docs-15`、`follow-dup-1476` 等用例第二轮的 `submissions`；`make demo` 的第二轮也能复现。
- 影响：第二轮仍然能闭环（编号 1、2 被旧结论占满），所以多轮追问类的流程闭环率对 FlashX 偏高；追问本身的正确率不受影响。
- 改进方向：executor 的提示里写明「子任务编号每条新消息从 1 开始，之前的结论已经记录」；更稳的做法是在图状态里按轮次记录已提交的子任务，只统计本轮新增的提交。

### 3.5 模型发来的编号是字符串

- 现象：GLM-4.7-FlashX 提交时把 `duplicate_of` 写成字符串 `"7687"`。工具的 Pydantic 参数模型按宽松模式把它转成整数，调用成功；但轨迹记录的是原始参数，打分时字符串和整数比较不相等，正确答案被判错。
- 处理：轨迹改为记录经过参数模型校验后的结论（`normalize_decision`），打分时按同样的规则把编号转成整数；打分改成每次都从原始轨迹重新计算（`rescore`），所以已有的运行结果也按修正后的规则统计。有对应的单元测试。

### 3.6 Gemini 3 多轮工具调用返回 400

- 现象：Gemini 走 OpenAI 兼容接口时，第一次工具调用之后的请求全部返回 400：`Function call is missing a thought_signature in functionCall parts`。
- 原因：Gemini 3 系列要求把上一轮返回的 thought signature 随工具调用原样带回，OpenAI 兼容接口的客户端会丢掉这个字段。
- 处理：Gemini 改用 LangChain 官方集成 `langchain-google-genai`，它会保留 thought signature。Agent 代码只依赖 `BaseChatModel`，切换只改了 `config.py`。
- 附带修正：原生集成返回的消息内容是分块列表而不是字符串，planner 解析计划时改用 LangChain 统一的 `.text` 属性。

### 3.7 免费额度的限流

- 现象：GLM-4.7-Flash 免费模型在并发时频繁返回 429「访问量过大」；Gemini 免费档按模型限制每分钟 15 次、每天 500 次请求。
- 处理：
  1. 区分错误类型：限流、过载、连接超时这类服务端错误整条用例重跑，最多 3 次，仍失败的单独计数，不和 Agent 自身的失败混在一起；请求格式错误（400）不重跑，直接计为失败。
  2. 给免费档模型加客户端限速（LangChain 的 `InMemoryRateLimiter`，全部会话共用一个）。
  3. 每条用例跑完立即写入 `traces.jsonl`，评测可以用 `--resume` 从中断处继续，已完成的用例不重跑，撞到限流的用例重跑。
  4. 主力国产模型换成付费但便宜的 GLM-4.7-FlashX，评测期间不受免费额度影响。

## 4 下一步

按预期收益排序：

1. 判重能力（3.3）：给 MCP server 加评论和关联 PR 工具，加候选比对步骤；这是重复 issue 目标的主要瓶颈。
2. 结构化一致性校验（3.2）：改动小，直接减少「判断对了但字段没填」的损失。
3. planner v2 设为默认（3.1），并在全部 40 条用例上复测，确认对其他类别没有副作用。
4. 按轮次统计提交（3.4），同时修正流程闭环率的统计口径。
